# CleanArch.API — Production Reference Implementation

.NET 8 Web API built with Clean Architecture, CRUD over a sample `Product` entity, Azure SQL,
Azure Key Vault, deployed to AKS with Application Insights + Log Analytics observability, and an
Azure Pipelines (Azure Repos) CI/CD pipeline.

## ⚠️ Read this first — what "working condition" means here

This was built in a sandboxed tool environment with **no network access to nuget.org**
(`api.nuget.org` returned `403 host_not_allowed` — verified, not assumed). That means:

- **I could not run `dotnet restore` / `dotnet build` / `dotnet test` here.** The .NET 8 SDK itself
  *is* installed and verified (`dotnet --version` → `8.0.130`), but package restore is blocked.
- Every `.cs` file was written by hand against the real package APIs (MediatR 12, EF Core 8,
  FluentValidation 11, AutoMapper 13, Azure.Identity, Serilog.AspNetCore, Asp.Versioning) and passed
  a mechanical brace/paren-balance and namespace check across all 46 source files — but that is
  **not** the same as a compiler pass. Treat this as a thorough, carefully-written draft that needs
  one real `dotnet build` on your machine (or in the pipeline below) before you trust it blindly.
- The EF Core migration (`Migrations/20260907000000_InitialCreate.cs`) was hand-authored to match
  `ProductConfiguration.cs` exactly, rather than generated by `dotnet ef migrations add`. Regenerate
  it for real once you can restore packages: delete the `Migrations` folder and run
  `dotnet ef migrations add InitialCreate -p src/CleanArch.Infrastructure -s src/CleanArch.API`.
- No Azure resources were actually deployed — I have no Azure credentials or cloud access from this
  sandbox. The Bicep/pipeline/K8s manifests are real, deployable IaC, not mockups, but they are
  unverified against a live subscription. Run `az deployment group what-if` first (the pipeline
  already does this as a gate).

**First three commands to run locally:**
```bash
dotnet restore CleanArchSolution.sln
dotnet build CleanArchSolution.sln -c Release
dotnet test tests/CleanArch.Application.UnitTests
```

## Assumption made explicit

You asked for CRUD APIs without naming the domain entity. I implemented `Product` (Id, Name,
Description, Price, StockQuantity, Sku, audit fields, soft delete, optimistic concurrency via
`RowVersion`) as the reference CRUD subject. Every other layer — repository, CQRS handlers,
EF configuration, controller, tests — follows an entity-agnostic pattern: swapping in your real
domain object is a mechanical copy-and-rename of `Product`'s five files, not a redesign.

## Architecture

```
src/
  CleanArch.Domain          — entities, domain exceptions, repository interfaces (no dependencies)
  CleanArch.Application     — CQRS (MediatR), FluentValidation, AutoMapper, DTOs, pipeline behaviours
  CleanArch.Infrastructure  — EF Core, Azure SQL, Key Vault-aware DI, health checks, resiliency (Polly)
  CleanArch.API             — controllers, Program.cs, Serilog + App Insights, security middleware, Dockerfile
tests/
  CleanArch.Application.UnitTests — handler + validator tests (Moq, FluentAssertions, xUnit)
infra/bicep/                — AKS, Azure SQL, Key Vault, ACR, VNet/NSG, Log Analytics, App Insights, alerting
k8s/                         — Deployment, Service, Ingress, HPA, PDB, NetworkPolicy, Key Vault CSI SecretProviderClass
pipelines/azure-pipelines.yml — Azure Repos/DevOps 4-stage pipeline (build/test → infra → image → AKS deploy)
docs/                        — RUNBOOK.md (failure scenarios), SECURITY.md (control list)
```

Dependency direction is strictly inward: `API → Infrastructure → Application → Domain`. Domain has
zero package references. Application depends only on `IApplicationDbContext`/`IProductRepository`
abstractions, never on EF Core directly — Infrastructure is the only project that references
`Microsoft.EntityFrameworkCore.SqlServer`.

## Key Vault: how the secret actually flows

1. Bicep (`modules/sql-secret.bicep`) writes the SQL connection string into Key Vault as secret
   `ConnectionStrings--DefaultConnection` (the `--` is Azure's convention for nested config keys).
2. **In Program.cs**, before any other configuration is read, `builder.Configuration.AddAzureKeyVault(uri, new DefaultAzureCredential())`
   pulls every secret into `IConfiguration`, keyed by name with `--` mapped to `:`. So
   `ConnectionStrings--DefaultConnection` in the vault becomes `configuration.GetConnectionString("DefaultConnection")`
   in code — no secret ever touches `appsettings.json` or an environment variable you'd accidentally commit.
3. **Identity, not a client secret**: `DefaultAzureCredential` resolves to AKS Workload Identity in
   the cluster (federated OIDC trust between the pod's ServiceAccount and an Azure AD Managed
   Identity — see `k8s/01-serviceaccount.yaml`), or your `az login` session locally. There is no
   Key Vault client secret/certificate anywhere in this repo, by design.
4. **Belt-and-braces**: the Key Vault CSI driver (`k8s/02-secretproviderclass.yaml`) *also* mounts
   the same secrets as a K8s Secret, so the same value is available two ways — the app doesn't need
   this (Program.cs already has it), but it lets other tooling (init containers, sidecars) read it
   without their own Key Vault calls.

Locally, `appsettings.Development.json` has a real LocalDB connection string checked in (no secret,
it's `Trusted_Connection=True`) so you can run without any Azure dependency at all.

## Running locally

```bash
cd src/CleanArch.API
dotnet run
# Swagger UI: https://localhost:<port>/swagger
```

`Database:MigrateOnStartup` is `true` in Development, so the LocalDB schema is created automatically
on first run. Auth is still enforced (JWT bearer) — for local testing without a real AAD tenant,
either stand up a dev IdP or temporarily comment out `[Authorize]` on the controller (do **not** ship
that change).

## Deploying

The pipeline (`pipelines/azure-pipelines.yml`) is the source of truth for the deploy sequence:

1. **BuildAndTest** — restore, build, unit tests, coverage, `dotnet list package --vulnerable`.
2. **InfraDeploy** — `az deployment group what-if` (preview, human-reviewable) then `create`, gated by
   an Azure DevOps **environment approval** on `production`.
3. **DockerBuildPush** — `az acr build` (the image is built *inside* ACR, source never leaves Azure,
   no Docker daemon needed on the agent); Defender for Cloud scans the pushed image.
4. **DeployToAKS** — `az aks get-credentials`, substitutes the real image tag into
   `k8s/04-deployment.yaml`, `kubectl apply -f k8s/`, then blocks on `kubectl rollout status` with a
   5-minute timeout. Because the Deployment's rolling-update strategy is `maxUnavailable: 0`, a
   failed/timed-out rollout does **not** cause an outage — old pods keep serving; follow up with
   `kubectl rollout undo`.

Required Azure DevOps variable group `cleanarch-prod-variables`: `azureServiceConnection`, `acrName`,
`resourceGroup`, `aksClusterName`, `sqlAdminPassword` (secret), `sqlAadAdminObjectId`.

See `docs/RUNBOOK.md` for failure-scenario playbooks and `docs/SECURITY.md` for the full control list.
